## The real root cause: a category mismatch, not a real failure
`task.yaml`'s own `completed_steps` (14 entries, checkpoints from 13:56 through
14:35) show the **worker actually finished 100% of the real audit+merge
scope**:

1. Cloned PR #293 head `8c73c550f3dc0c5f1358e8effc82b02b0cfa0423`, reviewed
   the real diff, independently reproduced the 2 pre-existing failing tests
   against `origin/main` (unrelated to the diff), ran the full suite on PR
   head (`2 failed, 564 passed`) and on the real merge tree.
2. Posted a fresh `AUDIT: PASS` comment on PR #293 naming that exact head
   SHA, superseding the earlier stale 10:51Z comment.
3. Re-verified the head SHA was unchanged immediately before merging, then
   **merged PR #293**.

Independently confirmed live via `gh pr view 293 --repo FChecklist/veridian-scripts`:
`mergedAt=2026-08-13T14:21:39Z`, `mergeCommit=c4fe5c8c9b57eaee93cf7d8f7d25d4b0003b482a`,
`headRefOid=8c73c550f3dc0c5f1358e8effc82b02b0cfa0423` (matches the audited/merged
SHA exactly), and a real `AUDIT: PASS` comment posted 2026-08-13T14:21:32Z naming
that head.

Because the real deliverable was **merging an existing PR in a different repo
(veridian-scripts)** via `gh`, the worker's own task branch (in `claude-control`)
legitimately had zero local commits -- there was nothing to commit locally, the
work product already lived on GitHub. The worker itself recognized this
correctly and routed to `pending_review` with an honest note: *"worker
finished, no changes to commit and zero commits ahead of master -- genuine
no-op, routing through pending_review ... so the supervisor gets the final
say."*

The **supervisor**, however, assumed every `pending_review` task must have its
own PR opened on its own worker branch, tried `gh pr create`/lookup for
`worker/task-20260813-135620-...`, found none (correctly -- this task's
deliverable was never going to have its own PR), and refused to proceed,
self-reporting `status=blocked`.

`reconcile_stale_running_workers.py`'s `_completion_candidates()` then only
checks the task's own `repo`/`branch` (`claude-control`) for a real commit/PR
-- it has no way to see `outputs_json.repo` (`veridian-scripts`) or
`completed_steps` text citing an external-repo PR merge. With zero candidates,
it fell through to the `task.yaml`-last-status=`blocked` branch and marked the
row `failed`.

This is the same category-mismatch bug class as the precedent RCAs
(`RCA_20260813_UMR-20260813-085615-c1dc.md`,
`RCA_20260813_UMR-20260813-105702-b694.md`): a real, honest evidence-gathering
gap in `_completion_candidates()` (it is scoped to the task's own
repo/branch, never an external-repo PR the task's own scope was to merge),
not a fabrication and not a genuine failure of the underlying work.
