## Real root cause
Same class of bug as the `ba95` precedent, different trigger mechanism:
this is not a cross-repo PR-lookup blind spot, it is a **race condition**
in whatever mechanical reconciler classifies rows as `killed`
(`reconcile_owner_dispatch_status.py` / the `STALE_LABEL_TERMINAL` rule).
The check evaluated "systemd inactive + no PR found + task.yaml not yet
`completed`" as sufficient evidence of an orphaned dispatch, but a worker
that has already pushed its commit and moved into
`pending_review` -> PR-create -> merge is not orphaned -- it is finishing
normally, just not yet reflected in the `umr_tasks` row's `outputs_json` at
the instant the check ran. The reconciler has no retry/grace-period before
writing a terminal `killed` label, so any task whose systemd unit exits
(unit lifecycle ends once its final `git push`/checkpoint completes, PR
creation happens in a later step) in the ~60-90s window before PR-open is
misclassified as `killed`.

This is a real, currently-unfixed gap: any future task whose worker
service exits before its supervisor's PR-create step lands will hit this
same race. Recorded here as a known follow-up (out of this RCA's scope,
which is "determine root cause and record the honest terminal outcome for
this one row" -- fixing the reconciler's race window needs its own
dedicated verification, per the same reasoning the `ba95` precedent used
for its own out-of-scope reconciler gap).
