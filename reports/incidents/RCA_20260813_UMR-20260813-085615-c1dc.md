## Real root cause of the "killed" mislabel
After finishing its real work, the worker's supervisor tried to open/find a
PR for **the task's own branch**,
`worker/task-20260813-085700-real-tier-1-independent-audit-of-pr--290`, in
**this task's own repo** (`claude-control`):

```
pull request create failed: GraphQL: Head sha can't be blank, Base sha
can't be blank, No commits between master and worker/task-20260813-085700-
real-tier-1-independent-audit-of-pr--290, Head ref must be a branch
PR_URL resolution FAILED ... refusing to continue ... (real incident: PR #84,
2026-07-26)
```

This is correct behavior by the supervisor: the task made **zero commits**
to `claude-control` (its real deliverable -- auditing and merging an
*external* PR -- lives entirely in a different repo, `veridian-scripts`), so
there was genuinely nothing to open a same-repo PR for, and the supervisor
correctly refused to silently fall back to an unrelated PR. It set
`task.yaml status=blocked` at `09:12:57` and stopped -- no live process
after that.

Some time later (`10:42:03`), an automated correction pass (almost
certainly `reconcile_owner_dispatch_status.py`'s `classify_row()`/
`apply_correction()`, run as part of the sibling task's one-off `--apply`
pass) inspected this row, found: systemd unit inactive, `task.yaml
status=blocked`, and **no merged PR matching this task's own branch name**
-- and concluded "no real deliverable", writing status=`killed`.

**That conclusion is false.** `classify_row()`'s evidence check is scoped
to a PR matching the row's *own task branch*, which is the right general
rule (a task's deliverable is normally a same-repo PR) but is a category
mismatch for this specific task's real scope: this task's job (per its own
SPEC) was to act as an independent auditor/merger of PR #290, an
**already-open PR in a different repo**, not to produce a new PR of its
own. A real, verifiable deliverable exists (AUDIT:PASS comment + merged PR
#290, confirmed live above) -- it is just not attributable via the
branch-matching heuristic `classify_row()` uses, so the mechanical
correction mislabeled a fully-successful task as an "orphaned dispatch...
never produced a real artifact."

This is the same root-cause shape as `UMR-20260813-100854-e8a1` (see
`ecbf6e5`, this repo's history): a task whose real, correct scope is
external-repo action produces zero commits in its own dispatch repo, the
supervisor correctly refuses to fabricate a same-repo PR, and a downstream
automated status-correction mechanism then misreads that as "no
deliverable." The two differ only in mechanism (e8a1 was stuck-task
SIGKILL after an unrelated worker-exit hang; c1dc was a `classify_row()`
mislabel with no SIGTERM at all) and in outcome (e8a1's PR #293 was still
unmerged at RCA time -> `completed_unmerged`; c1dc's PR #290 is **already
merged** -> `completed`, below).

## Out of scope, flagged for a future task
`reconcile_owner_dispatch_status.py`'s `classify_row()` should not label a
row "orphaned dispatch, never produced a real artifact" solely because no
PR matches the task's own branch -- it should also check whether the
task's own audit/session record (e.g. a posted `AUDIT:PASS` comment or
merge action cited in `task.yaml`'s `completed_steps`) points at a real,
independently-verifiable external PR/commit before concluding "no real
deliverable." This is the second real occurrence of the same category
mismatch (`e8a1`, `c1dc`) and is worth a dedicated fix.
