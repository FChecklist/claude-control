# RCA: shared PROGRESS.md causes empty-fix PRs + universal merge conflicts

GOVERNING CHAIN: UMR-20260806-171945-5767 (P1 deterministic foundation) -> UMR-20260813-195922-f548

## Real defect

Every worker rewrote **the same file, `PROGRESS.md`**, on its own branch. The real, current worker template line, `worker-entrypoint.sh`'s `PROGRESS_INSTRUCTION` (confirmed live -- this exact string is echoed verbatim into this very task's own dispatch prompt, so it is not a stale/superseded copy):

```
PROGRESS_INSTRUCTION="PROTOCOL: maintain PROGRESS.md (## Completed / ## Remaining, markdown checkboxes), update after each step. commit+push after each meaningful unit, not only at the end. on a 2nd consecutive failure of the identical approach: STOP, do not attempt a 3rd time -- this is enforced by a circuit breaker on the next invocation regardless, so stopping yourself first saves a wasted restart."
```

This is a literal instruction to edit one shared path with no per-task namespacing, and the worker template treats "wrote PROGRESS.md" as satisfying the whole commit requirement -- there was no check anywhere that the diff actually touched code.

## Fix (real code, in FChecklist/veridian-scripts, not this repo)

Implemented in a fresh, isolated clone of `veridian-scripts` (deliberately **not** the live shared `/opt/veridian/scripts` checkout on this host, which had 6 unrelated files with uncommitted changes from other concurrently-running workers at the time -- editing it directly would have mixed unrelated in-flight work into this fix's diff):

1. `worker-entrypoint.sh`: `PROGRESS_INSTRUCTION` and the `RESUME` prompt now point every worker at its own `progress/<task_id>.md` instead of the shared `PROGRESS.md`. A new path per branch never collides on merge.
2. `progress_completion_gate.py` (new): a real, mechanical completion gate, not a prompt instruction.
   - `check-completion`: if a task's `prompt.txt` names a specific source/script file, that file must appear in the real diff (committed + staged + unstaged vs the merge-base with `origin/$DEFAULT_BRANCH`). A non-empty diff that doesn't touch it fails with an explicit reason.
   - `rollup`: deterministically regenerates one rolled-up view from every `progress/*.md` file. Generated output only -- no worker branch ever writes to it.
3. `worker-entrypoint.sh` wires `check-completion` in right before the quality-gate loop. A rejection checkpoints the task `blocked` with the real reason, pushes whatever exists, and exits -- never silently marked complete.
4. Deprecation banner added to the legacy root `PROGRESS.md` (left in place as historical record, not deleted).

## Cross-repo precedent found while implementing (important, not previously cited by the SPEC)

This repo (`claude-control`) **already hit and fixed problem (B) for its own `PROGRESS.md`**, by a different mechanism than the one implemented here. `.gitignore` (this repo, lines 5-12):

```
# PROGRESS.md is a per-workspace worker scratch file (see scripts/veridian-task.py
# cmd_create / worker-entrypoint.sh). Every task branch writes its own narrative into
# it, so tracking it in git guaranteed a merge conflict whenever 2+ task branches
# diverged from and merged back into master close in time (hit PR12, PR23, PR24, PR27).
# It is intentionally untracked now -- durable records live in each task's own
# checkpoint history (task.yaml, read via `veridian-task.py resume-context`), which
# already parses this file straight off disk and does not depend on git tracking it.
PROGRESS.md
```

i.e. `claude-control`'s fix is to **never track `PROGRESS.md` in git at all** -- it stays a local, untracked, per-workspace scratch file, and durable history lives in `task.yaml`/checkpoint records instead. That trivially prevents conflicts (an untracked file can't conflict) and, as a side effect, would also have prevented problem (A) here (a diff that is only an untracked-file edit is empty, and `worker-entrypoint.sh`'s own `NOOP-COMPLETION-BLOCK` already routes a genuinely empty diff to `pending_review` rather than a false "completed").

**veridian-scripts's `PROGRESS.md` is tracked in git** (confirmed: `git log --oneline -- PROGRESS.md` shows real history, e.g. commits `b22bf55`, `646d142`), so it never got this fix -- that gap is the proximate cause of both (A) and (B) there.

This was found *during* implementation, not before, so PR #322 does **not** adopt the untracked-scratch-file approach -- it instead implements what the dispatching SPEC explicitly asked for (per-task, git-tracked `progress/<task_id>.md` files + a deterministic rollup + a real completion gate), which has a real advantage the untracked approach doesn't: the per-task narrative is visible in the PR diff itself for human review, not just in a local scratch file. Flagged here, and as a comment on veridian-scripts#322, as a legitimate alternative worth a maintainer decision -- not re-implemented in this pass to avoid discarding already-tested, already-pushed work on a judgment call this task wasn't asked to make.
