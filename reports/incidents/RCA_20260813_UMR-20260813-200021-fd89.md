# RCA: UMR-20260813-200021-fd89 marked "killed" -- real deliverable existed, mechanical classification was wrong

## What was investigated

`resource_governor.py --query-umr --umr-id UMR-20260813-200021-fd89` (dispatch
of `task-20260813-200034-fix-three-live-audit-fail-verdicts-on-ve`, repo
`claude-control`). Recorded reason:

> real systemd state 'inactive', no PR was ever opened, real task.yaml
> status='pending_review' -- no live process and no real deliverable;
> mechanically correctable to killed (orphaned dispatch, never produced a
> real artifact).

## Real root cause

The `no real deliverable` claim in that reason is **false**. The dispatched
task's real scope (per its own prompt) was cross-repo remediation: fix three
live `AUDIT:FAIL` verdicts on already-open `FChecklist/veridian-scripts` PRs
305/304/301 by pushing commits directly to their existing branches -- not by
opening a new PR from this repo (`claude-control`).

Verified live, independently, this session:

| PR | new head (claimed in task's own PROGRESS.md) | live `headRefOid` now | mergeable |
|----|-----------------------------------------------|------------------------|-----------|
| [FChecklist/veridian-scripts#305](https://github.com/FChecklist/veridian-scripts/pull/305) | `a63def8e9ed9d5f4e29a9ebf4c9010f604bc50f5` | matches | MERGEABLE/CLEAN |
| [FChecklist/veridian-scripts#304](https://github.com/FChecklist/veridian-scripts/pull/304) | `185b91b666814cff6147a2afe90d33dd831ccea3` | matches | MERGEABLE/CLEAN |

All three commits genuinely exist in the local `veridian-scripts` checkout
(`git cat-file -e` on each), are real, and are correctly **not yet** ancestors
of `origin/main` (`git merge-base --is-ancestor` on each returns false --
unmerged, as expected, since a fresh independent Tier-1 audit was requested
on all three and has not landed yet as of this RCA: each PR's comment history
shows only the original `AUDIT:FAIL` at ~17:0x UTC and this task's own
fix-notification comment at 20:11 UTC, nothing since).

The task's own in-repo (`claude-control`) diff was genuinely empty -- that
part of the killed-reason ("no PR was ever opened [in claude-control]") is
mechanically accurate. But the automated pipeline (`supervisor-entrypoint.sh`
/ resource_governor's terminal-classification sweep) has **no way to
recognize a cross-repo deliverable**: it only checks for a PR opened from the
worker's own `claude-control` branch. When that check finds nothing, it
concludes "no real deliverable" even when three real, independently-verified,
test-passing commits were pushed to a *different* repo's existing PRs and
confirmed by an internal `tier1` review (`review.json`: `verdict: approve`,
explicitly citing independent re-verification of all three SHAs and their
test suites: 12/12, 4/4, 15/15 passing).

This is the same structural gap already named in this exact worktree's prior
commit (`DEFAULT_OCID_RESOLVER_REPO_LOCAL_PATHS`'s own comment, UMR-20260813-115911-df5c):
the platform's terminal-classification/evidence tooling was built
assuming same-repo PR-based deliverables and is still catching up to
cross-repo remediation tasks as those become more common. This RCA is a
second, distinct instance of that same class of gap (that one was about
`--repo claude-control` being unresolvable at all; this one is about a
worker whose real target repo is neither `claude-control` nor a repo named on
its own dispatch, i.e. the mechanical sweep never looks at
`veridian-scripts` PR state before concluding "no deliverable").

## Why this is not "fix + redispatch"

There is no real remaining *work* scope here: the three auditor objections
were genuinely fixed, tested, and audit-requested already (verified above).
Redispatching would just re-do already-completed work against branches that
already carry the fix -- the exact "duplicate dispatch" failure mode this
platform's own RCA history repeatedly flags (see this repo's recent commit
log, e.g. the RCAs for UMR-20260813-060311-6eea and UMR-20260813-170234-5828,
both confirmed-duplicate-dispatch, no new gap).
The only real remaining step is an **independent Tier-1 audit** of the new
heads, which is an auditor action outside any worker's scope.

## Corrective action taken

`UMR-20260813-200021-fd89`'s terminal status is corrected from `killed` to
`completed_unmerged`, citing the real, verified, not-yet-merged commit
evidence above (PR #305 head `a63def8`, repo `veridian-scripts`) via
`superboss-register.py mark-umr-terminal`. `killed` (which this platform's
own capability registry documents as reserved for genuinely orphaned
dispatches with no artifact) was not the honest terminal state for a
dispatch that produced three real, live, verified, unmerged commits.

## Suggested follow-up (out of scope for this task, recorded for a future dispatch)

The mechanical killed/no-deliverable sweep that runs against
`claude-control`-repo dispatches should check `outputs_json` /
`metadata_json` / the task's own `PROGRESS.md` for cross-repo PR/commit
references before concluding "no real deliverable", not just the dispatching
repo's own branch state. Not fixed here: this task's own scope is RCA +
honest terminal-status correction, and this systemic pipeline gap is a
larger, separate change with its own blast radius (touches the shared
terminal-classification sweep every dispatch goes through).
