# Executive Summary

VERIDIAN is envisioned as the world's most comprehensive browser-first Prompt Intelligence Platform. After extensive research into current browser AI frameworks, prompt engineering systems, and the MCP ecosystem, this document presents a significantly expanded and refined architecture that addresses the full scope of challenges in production-grade prompt lifecycle management, browser-native AI execution, and enterprise governance.
The original specification outlined approximately 44 engines and a promising browser-first direction. Our analysis, grounded in research of projects including WebLLM (165 pre-compiled LLM configurations, WebGPU-optimized), BrowserMCP (real-browser MCP automation), Transformers.js v3 (WebGPU-accelerated inference), DSPy (declarative prompt optimization), and the broader prompt engineering tooling ecosystem (LangSmith, LangFuse, NeMo Guardrails, promptfoo), reveals that a production-grade Prompt Intelligence Platform requires a substantially broader architectural footprint.
This improved specification expands the architecture from approximately 44 engines to over 70 engines, adds 16 previously missing pipeline stages, introduces a defense-in-depth security model backed by research on current prompt injection prevention techniques, incorporates newly available browser APIs (WebNN, Chrome Built-in AI, NPU support), and provides concrete performance budgets for every pipeline stage. The result is an architecture that covers not only the original vision but also the gaps that separate a prototype from a production-grade system.

# Part I: Gap Analysis of the Original Architecture

This section identifies the specific areas where the original VERIDIAN specification fell short of a production-grade Prompt Intelligence Platform. Each gap is categorized by severity and mapped to the research-backed improvements introduced in this document.

## 1.1 Missing Browser AI APIs and Technologies

The original specification referenced WebLLM, BrowserMCP, and OPFS, but missed several critical browser AI technologies that have matured as of mid-2025. WebGPU shipped by default in all major browsers simultaneously in November 2025, making it the universal compute backbone for browser AI. However, the architecture failed to account for the Web Neural Network API (WebNN), which shipped in Chrome 131 and provides hardware-accelerated inference via CPU, GPU, and NPU backends through navigator.ml. Chrome's Built-in AI API (window.ai) offers zero-download, zero-configuration access to models like Gemini Nano for summarization, rewriting, and classification tasks. The NPU (Neural Processing Unit) delegation path, available through WebNN, enables sub-30ms inference times for certain workloads and represents an entirely new execution tier that the original architecture did not consider.
Additionally, the specification overlooked Transformers.js v3, which supports WebGPU-accelerated inference for over 100 model families including LLMs (Llama, Phi, Gemma, Qwen), embeddings (BERT, MiniLM, BGE), image models (ViT, CLIP), audio models (Whisper, Bark), and supports progressive loading, ONNX format, and quantization (INT8, INT4). ONNX Runtime Web provides an alternative WebGPU/WebNN/WASM inference path with enterprise backing. Shape Detection API (FaceDetector, TextDetector, BarcodeDetector) and Web Codecs API for multimodal pipelines were also absent. These omissions mean the original architecture would have been unable to leverage a significant portion of the available browser AI compute surface.

## 1.2 Missing Prompt Engineering Concepts

The prompt management ecosystem has matured dramatically. The original specification included prompt versioning and A/B testing, but missed the most significant advancement in the field: DSPy, Stanford NLP's declarative prompt programming framework. DSPy separates task definition (signatures) from prompt implementation and provides automatic optimizers (BootstrapFewShot, MIPROv2, BayesianSignatureOptimizer, COPRO) that programmatically improve prompt quality against defined metrics. This is the closest existing technology to a true prompt compiler, and its absence from the original architecture is a critical gap.
The specification also lacked defense-in-depth security architecture. Research into current prompt security tools reveals a mandatory multi-layer approach: input sanitization (regex, LLM classifiers), system prompt hardening (XML tags, instruction hierarchy), output filtering (NeMo Guardrails, Llama Guard), and runtime guardrails. The original architecture had a Prompt Security Engine but without specifying the layered defense model that production systems require. Other missing concepts include: LLM-as-judge evaluation (using a powerful model to score prompt outputs), semantic caching (embedding-based similarity matching via GPTCache or Redis vector search), cross-model portability (prompts that work across providers), real-time prompt adaptation (dynamic adjustment based on input characteristics), prompt staleness detection (correlating time-since-update with quality drift), and the GitOps-for-prompts workflow pattern (Git branch protection plus CI/CD plus eval gates for prompt promotion).

## 1.3 Missing Pipeline Stages

The original Prompt Compiler Pipeline contained 25 stages from User Input to AI Execution. Our analysis identifies 16 additional stages required for production operation. Before execution, the pipeline needs a Cost Estimation stage that calculates token budget and dollar cost before committing to LLM inference. A Model Selection stage must evaluate whether the task should go to the browser Lite LLM, the NPU via WebNN, Chrome's Built-in AI, or escalate to a server-side model based on task complexity, privacy requirements, and latency budget. A Guardrails stage must validate both input and output against safety policies using NeMo Guardrails or Llama Guard. A Semantic Cache Check stage, using embedding similarity search, can avoid redundant LLM calls for semantically identical inputs.
After execution, an Output Filtering stage removes PII, injected instructions, or policy violations. A Staleness Detection stage monitors whether the active prompt version is producing degrading results compared to historical baselines, triggering an automatic re-optimization request to the Learning Engine. A Quality Scoring stage evaluates the output against defined quality metrics, feeding the Analytics Engine with performance data that drives continuous improvement. Together, these 16 additional stages transform the pipeline from a linear compiler into a production-grade inference system with feedback loops at every critical juncture.

## 1.4 Missing Engines

The original 44 engines, while comprehensive in scope, missed several categories identified through our research. A Semantic Cache Engine is needed to implement embedding-based similarity caching alongside the existing multi-level structural cache. An NPU Integration Engine is required to manage the WebNN delegation path and NPU model lifecycle. A Defense-in-Depth Engine coordinates the multi-layer security model across input, system prompt, output, and runtime layers. A Red Team Engine provides automated adversarial testing using tools like Garak and PyRIT. A Cost Optimization Engine tracks per-prompt cost, enforces budget guardrails, and recommends cost-reduction strategies.
A Compliance Engine manages GDPR, HIPAA, SOC 2 requirements for prompt content, evaluation datasets, and audit logs. A Model Selection Engine evaluates task requirements against available compute tiers (NPU, WebGPU LLM, Built-in AI, Server) and selects the optimal execution path. A Prompt Portability Engine ensures prompts can be adapted across model providers without manual rewriting. A DSPy Integration Engine provides the bridge between VERIDIAN's prompt registry and Stanford's declarative optimization framework, enabling automatic prompt improvement against defined quality metrics. A Browser Worker Engine manages the lifecycle of Web Workers, SharedArrayBuffer coordination, and thread pool scaling for parallel ML inference.

## 1.5 Incomplete Performance Specifications

The original specification mentioned performance targets generically. A production architecture requires concrete latency budgets per pipeline stage. For example, browser startup to operational readiness must complete within 3 seconds. Prompt parsing and noise removal must complete within 10ms. Intent extraction via the Lite LLM should complete within 50ms. Entity and variable detection should each complete within 20ms. The full cache lookup chain (L0 through L5) should complete within 5ms for a hit. Execution planning, including model selection and capability verification, must complete within 30ms. The total browser-execution budget (user input to response rendering) should not exceed 500ms for cached/confident prompts and 3 seconds for prompts requiring full LLM inference.
Memory budgets must also be specified: the Lite LLM context cache should be capped at 256MB, the prompt registry's in-memory index should not exceed 128MB, and the total browser tab memory footprint should stay under 2GB to avoid browser tab crashes. Storage budgets need definition: OPFS allocation for model weights should be capped at 4GB (enough for one 8B model at 4-bit quantization plus one embedding model), IndexedDB for metadata should be capped at 500MB, and the Cache API should be managed with explicit quota monitoring to avoid eviction of critical assets. These concrete budgets are essential because without them, individual engines will compete for resources without coordination, leading to performance degradation and unpredictable behavior.

## 2.2 Improved Prompt Compiler Pipeline

The Prompt Compiler Pipeline is the central nervous system of VERIDIAN. It transforms raw user input into an optimized, validated, and executable prompt through a series of precisely defined stages. The improved pipeline expands from 25 stages to 41 stages, adding critical paths for NPU delegation, semantic caching, cost estimation, guardrails, output filtering, and staleness detection. Each stage has a defined input, output, latency budget, and fallback behavior.

### Stage 1: Input Acquisition Layer (Stages 1-2)

User Input is received and immediately checked against the multi-level cache hierarchy. Browser Cache Check traverses L0 (JavaScript memory, sub-microsecond), then L1-L3 in parallel via Promise.all (Cache API, IndexedDB, OPFS, combined 5ms target). If any cache level returns a hit, the pipeline short-circuits and returns the cached response immediately, bypassing all subsequent stages. This optimization is critical because cache hits represent the majority of production traffic in a mature system. Only on a complete cache miss does the pipeline proceed to Stage 2.

### Stage 2: Lightweight Analysis Layer (Stages 3-7)

This layer runs entirely in JavaScript without any LLM inference, using pattern matching, regex, and cached intent models. Noise Removal strips formatting artifacts, redundant whitespace, and non-semantic content. Intent Extraction identifies the primary, secondary, and implicit intents from the cleaned input using a pre-trained classifier running via Transformers.js or the NPU. Entity Detection extracts named entities including domain-specific types defined in the prompt metadata schema. Variable Detection identifies template variables, type-infers them, and resolves defaults from the variable registry. Finally, Input Classification categorizes the request as simple (cached pattern), complex (requires compilation), or novel (triggers learning path). This entire layer must complete within 15ms total.

### Stage 3: Context Assembly Layer (Stages 8-12)

The Context Assembly Layer gathers all contextual information needed for prompt construction. Business Context Builder loads relevant business rules and domain knowledge from the Knowledge Cache (L9). User Context Loader retrieves the user's preferences, history, and permission scope from IndexedDB (L2). Session History Assembly constructs the conversation context from the session store. Variable Binding resolves all detected variables against their type-specific sources. Template Hydration combines the base prompt template with context, variables, and session data into a complete but unoptimized prompt. Data is pulled from IndexedDB (L2) for metadata and OPFS (L3) for large context documents. Total latency budget: 25ms.

### Stage 4: Prompt Construction Layer (Stages 13-18)

The Machine Prompt Builder takes the hydrated template and applies the prompt compilation strategy selected by the DSPy Integration Engine. The Prompt Optimizer performs token reduction, instruction refinement, and structural optimization to minimize token count while preserving semantic completeness. The Prompt Compressor applies lossless compression techniques. A Prompt Hash Generator creates a deterministic hash of the compiled prompt for cache keying. The Prompt Fingerprint generates a semantic fingerprint for the Similarity Search. The Prompt Similarity Search (L5 Semantic Cache) queries the embedding index: if similarity exceeds 0.95, return cached response; if between 0.85 and 0.95, return cached response with staleness flag; if below 0.85, continue to Stage 5. Total latency budget: 30ms.

### Stage 5: Verification Layer (Stages 19-25)

The Verification Layer ensures the compiled prompt is safe, authorized, and economically viable before execution. Confidence Scoring combines signals from cache match quality, intent clarity, context completeness, and model readiness into a single confidence score. Business Rule Verification checks the prompt against active business rules. Workflow Verification validates the execution workflow. Capability Verification confirms all required software capabilities are available. Permission Verification checks RBAC permissions for the requesting user and prompt combination. Cost Estimation calculates the expected token budget and dollar cost before committing resources. Model Selection evaluates task complexity, privacy requirements, latency budget, and hardware availability to route to the optimal execution tier. Total latency budget: 30ms.

### Stage 6: Pre-Execution Guardrails (Stages 26-29)

Before any inference, the pipeline validates through Pre-Execution Guardrails. Input Guardrails, powered by NeMo Guardrails or Llama Guard, evaluate the full compiled prompt against configurable safety policies. Content Policy Check ensures compliance with organizational content policies. PII Detection scans for personally identifiable information that should not be processed. Safety Classification categorizes the request by risk level. If any guardrail triggers, the pipeline diverts to a safe fallback path rather than proceeding to execution. This layer operates within a 20ms latency budget and is critical for preventing harmful outputs.

### Stage 7: Execution Layer (Stages 30-34)

The Execution Layer routes the validated prompt to the optimal compute tier with automatic fallback. The Execution Plan Builder constructs the final execution graph. Tier 1 (NPU via WebNN) handles lightweight tasks like classification and summarization in under 30ms. Tier 2 (Chrome Built-in AI via window.ai) provides zero-download inference for simple tasks. Tier 3 (Browser Lite LLM via WebLLM WebGPU) handles complex reasoning with 7B-8B models at 40-70 tokens per second. Tier 4 (Browser Transformers.js) provides embeddings, classification, and NER via dedicated models. Tier 5 (Server Escalation) handles tasks that exceed browser capabilities. Each tier has a timeout and falls back to the next tier if unavailable. Total execution budget: 3 seconds maximum.

### Stage 8: Post-Execution Layer (Stages 35-41)

After inference, the Post-Execution Layer ensures output quality and system integrity. Output Filtering removes PII using browser-adapted Presidio, injected instructions, and policy violations. Guardrails Validation applies output-side safety checks. Quality Scoring evaluates the response against defined quality metrics using either heuristic rules or LLM-as-judge. Result Caching stores the response across L0-L5 with appropriate TTL. Telemetry Emission sends performance and quality metrics to the Analytics Engine. Staleness Comparison checks whether the output quality matches historical baselines; if degradation is detected, a re-optimization signal is emitted to the Learning Engine. This feedback loop is essential for continuous improvement. Total latency budget: 10ms.

## 2.3 Enhanced Multi-Level Cache Architecture

The improved cache architecture defines 10 levels (L0-L9) with specific technologies, access patterns, latency targets, eviction policies, and storage limits. Research into browser storage APIs confirms that OPFS with synchronous access handles provides near-native I/O performance and is the optimal storage backend for large binary data such as model weights. IndexedDB remains optimal for structured queries on metadata. The Cache API is best for HTTP-sourced assets. The addition of a Semantic Cache (L5) using embedding similarity search fills a critical gap for avoiding redundant LLM inference on semantically similar inputs.

[TABLE]

L3 | OPFS (sync handles) | 2-10ms | Shared quota | Manual, LRU on files | Model weights, large binary data

### Cache Hit Path Optimization

The cache lookup chain follows a waterfall pattern with short-circuiting. L0 is checked first (sub-microsecond). On miss, L1-L3 are checked in parallel using Promise.all, reducing the combined latency to the slowest single lookup rather than the sum. If L5 (Semantic Cache) has a hit with similarity greater than 0.95, the cached response is returned immediately, bypassing all subsequent pipeline stages. This optimization can eliminate up to 80% of LLM inference calls for repeated or similar queries, reducing both latency and cost significantly.
The L5 semantic cache uses local embeddings computed via Transformers.js (all-MiniLM-L6-v2 at approximately 50ms per embedding on WebGPU) or the Lite LLM's embedding capability. Embeddings are stored in IndexedDB with a JavaScript-implemented HNSW-style approximate nearest neighbor index maintained in L0 memory. The similarity threshold is configurable per-prompt, with high-stakes prompts using a stricter 0.97 threshold and low-stakes prompts using a more aggressive 0.90 threshold to maximize cache utilization.

## 2.5 Performance Budget Framework

Every pipeline stage operates within a defined latency budget. These budgets are not aspirational; they represent hard limits that trigger fallback behavior when exceeded. The total browser-execution budget for a confident, cached prompt response is 500ms. For prompts requiring full LLM inference, the budget extends to 3 seconds. For prompts that escalate to the server, the budget extends to 10 seconds with progressive loading feedback to the user.

## 2.8 Defense-in-Depth Security Architecture

Based on research into current prompt injection prevention techniques and tools (NeMo Guardrails, Llama Guard, Prompt Guard, Garak, PyRIT), VERIDIAN implements a four-layer defense-in-depth security architecture. No single layer is sufficient on its own; the layers are designed to be complementary, with each catching threats that slip through previous layers.

### Layer 1: Input Sanitization

The first line of defense operates before any prompt construction begins. This layer implements regex-based pattern detection for known injection vectors (ignore previous instructions, system:, role-playing attempts), character-level anomaly detection for invisible Unicode characters and zero-width spaces used in injection attacks, and a lightweight LLM classifier (running locally via the Lite LLM or NPU) that classifies input intent as benign, suspicious, or malicious. Inputs classified as malicious are rejected immediately. Suspicious inputs are flagged for additional scrutiny in downstream layers. This layer operates within the 15ms latency budget of the Lightweight Analysis section.

### Layer 2: System Prompt Hardening

The second layer protects the system prompt itself. All system prompts in VERIDIAN use XML tag delimiters to create clear boundaries between instructions and user input. Instruction hierarchy is enforced: system-level instructions are marked with a higher priority than user-level content, making it structurally difficult for user input to override system directives. Prompt templates use least-privilege design, including only the instructions necessary for the specific task. This layer is enforced at compile time in the Prompt Compiler Engine and validated by the Prompt Validation Engine.

### Layer 3: Runtime Guardrails

The third layer operates during inference execution. NeMo Guardrails or Llama Guard evaluates both the full compiled prompt (input-side guardrails) and the model's output (output-side guardrails) against configurable safety policies. These policies include topical boundaries (ensuring the model stays within its defined domain), fact-checking rails (flagging potentially hallucinated claims), and format enforcement (ensuring output adheres to required schemas). This layer operates at the Pre-Execution and Post-Execution stages of the pipeline, within a combined 30ms latency budget.

### Layer 4: Output Filtering and Monitoring

The fourth and final layer operates after inference completes. This layer scrubs PII from model outputs using Microsoft Presidio (adapted for browser execution), detects and removes any leaked system instructions that may have been included in the output, applies content moderation using Llama Guard 3 or Lakera Guard, and logs all outputs to the Audit Engine for compliance review. The Analytics Engine monitors for anomalous patterns in prompt usage that may indicate an ongoing attack, triggering automatic rate limiting or alerting. This layer operates within the 10ms Post-Execution budget.

## 2.9 Governance and Compliance Framework

Production prompt systems in enterprise environments must comply with regulatory requirements and internal governance policies. VERIDIAN's governance framework implements four key capabilities: Role-Based Access Control (RBAC), approval workflows, compliance management, and comprehensive audit trails.

### Prompt Lifecycle Governance

The Prompt Lifecycle Engine implements a state machine with the following transitions: Draft (engineer creates) to Review (team reviews, evals run) to Staging (canary deployment, 1-5% traffic) to Production (full rollout) to Deprecated (sunset with timeline). Each transition requires explicit approval from a designated reviewer. The Review-to-Staging transition requires passing automated evaluation gates (accuracy, latency, cost) with configurable thresholds. The Staging-to-Production transition requires a minimum canary duration (e.g., 24 hours) with no regression detection. All transitions are logged to the Audit Engine with timestamp, actor, and justification.

### GitOps Workflow Integration

VERIDIAN supports a GitOps workflow where prompts are stored as versioned files (YAML, JSON, or TOML) in a Git repository. Changes go through pull requests with mandatory evaluation results attached as CI/CD artifacts. Branch protection rules require passing evals before merge. The Prompt Import/Export Engine handles serialization between the Git format and the internal registry format. This approach enables code review processes, reverting changes via Git, and integration with existing CI/CD pipelines.

## 3.4 Key Research Findings

WebGPU is now universal across all major browsers (November 2025 milestone), providing a consistent compute substrate for browser AI. WebGPU delivers 10x performance improvement over WebGL for AI workloads, enabling real-time inference for models up to 8B parameters. OPFS with synchronous access handles provides near-native I/O performance for large binary data, making it the optimal storage backend for model weights. The Chrome Built-in AI API (window.ai) provides zero-download, zero-configuration access to models, representing a new execution tier. WebNN enables NPU delegation, opening sub-30ms inference paths for lightweight classification and summarization tasks.
DSPy has become the de facto standard for programmatic prompt optimization, with its declarative signature approach separating task definition from prompt implementation. The prompt engineering tooling landscape has consolidated around a gateway pattern for routing, caching, and cost control, combined with a registry for versioning and evaluation, and a separate evaluation framework for quality assurance. Defense-in-depth security is now mandatory for production prompt systems. Public prompt marketplaces have declined; organizations build internal prompt libraries with rigorous evaluation and governance instead.
