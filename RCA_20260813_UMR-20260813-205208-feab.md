# RCA: UMR-20260813-205208-feab marked "killed" -- real deliverable existed, mechanical classification was wrong

## What was investigated
`resource_governor.py --query-umr --umr-id UMR-20260813-205208-feab` (dispatch of
`task-20260813-210004-re-audit-then-merge-veridian-scripts-pr`, repo `claude-control`,
tier 1, source `owner_dispatch_gateway`). Recorded reason:

> real systemd state 'inactive', no PR was ever opened, real task.yaml
> status='pending_review' -- no live process and no real deliverable;
> mechanically correctable to killed (orphaned dispatch, never produced a
> real artifact).

## Real root cause
The `no real deliverable` claim is **false**. This is the exact same
mechanical mis-classification bug as its own immediate predecessor,
**UMR-20260813-200021-fd89** (see `RCA_20260813_UMR-20260813-200021-fd89.md`,
merged via PR #182): the terminal-classification sweep only checks whether a
PR was opened *from the claude-control worker branch*. It has no visibility
into cross-repo deliverables -- here, a real audit verdict posted as a
**GitHub PR comment on an external repo**, `FChecklist/veridian-scripts#305`.

The dispatched task's real scope (per its own prompt) was: re-audit PR 305 at
head `a63def8e9ed9d5f4e29a9ebf4c9010f604bc50f5` (superseding a stale FAIL
verdict against an earlier head), run the real test suite, post a real
AUDIT:PASS/FAIL naming the exact head, and merge **only** on a real PASS.

Verified live, independently, this session:

1. **`gh api repos/FChecklist/veridian-scripts/issues/305/comments`** shows a
   real comment from `FChecklist` at `2026-08-13T21:03:05Z` (matches the
   task's own `pending_review` checkpoint at `21:03:25Z`), titled
   `## AUDIT:FAIL`, naming head `a63def8e9ed9d5f4e29a9ebf4c9010f604bc50f5`
   explicitly, with:
   - `tests/test_quality_gate_docs_only.py`: 12 passed, exit 0 (real re-run).
   - Independent end-to-end re-test (own harness, real git repos, not the
     PR's own test code) of the 5 originally-FAILed cases
     (`requirements.txt`, `pyproject.toml`, `ci.yml`, `.eslintrc.yml`,
     `Dockerfile`) -- all confirmed genuinely fixed.
   - A real, reproducible finding that the fix is incomplete for the general
     bug *class*: `.cfg`/`.ini` (`setup.cfg`, `tox.ini`, `pytest.ini`),
     `.lock` (`yarn.lock`, `Cargo.lock`, `poetry.lock`), dotfile configs
     (`.flake8`, `.babelrc`, `.env`, `.dockerignore`, `.gitattributes`), and
     extensionless build files (`Gemfile`, `Rakefile`, `Vagrantfile`) are all
     still misclassified `DOCS_ONLY=1`, with exact repro commands given.
   - A correct, explicit **do-not-merge** decision, matching the task's own
     required step E ("Merge PR 305 ONLY on a real PASS ... On FAIL do not
     merge").
2. **`/opt/veridian/repos/veridian-scripts`** (local checkout): `git fetch
   origin +refs/pull/305/head`, then `git cat-file -e
   a63def8e9ed9d5f4e29a9ebf4c9010f604bc50f5` succeeds (real, fetchable
   commit) and `git merge-base --is-ancestor
   a63def8e9ed9d5f4e29a9ebf4c9010f604bc50f5 origin/main` returns false --
   correctly **not** merged, consistent with the real FAIL verdict.
3. The task's own `task.yaml` / `PROGRESS.md` on disk (task dir
   `task-20260813-210004-re-audit-then-merge-veridian-scripts-pr`) record
   every one of the above steps as completed, ending in `remaining_steps:
   None -- audit complete, verdict is FAIL, PR left unmerged pending a
   further fix + fresh audit at the next head`.

Zero commits landed in `claude-control` (the repo `resource_governor.py`
checks) -- but that is the **expected, correct** shape of an audit-only
task's diff, not evidence of an orphaned dispatch. The task's own
`task.yaml` status was `blocked`, not because the audit failed to run, but
because its supervisor could not open a `claude-control` PR for a genuinely
empty branch diff ("worker finished, no changes to commit and zero commits
ahead of master -- genuine no-op"). `resource_governor.py`'s downstream sweep
then mechanically read that as "orphaned dispatch, never produced a real
artifact" -- which conflates "no `claude-control` PR" with "no deliverable
at all", the same conflation identified and corrected in fd89's RCA.

## Correction applied
`superboss-register.py mark-umr-terminal --umr-id UMR-20260813-205208-feab
--status completed_unmerged --commit-sha
a63def8e9ed9d5f4e29a9ebf4c9010f604bc50f5 --repo veridian-scripts --pr-number
305 --reason "..."` -- the structured-evidence gate independently verified
the commit is real (`git cat-file -e`) and genuinely not yet an ancestor of
`origin/main`, so the write was accepted (not refused).

`completed_unmerged` (rather than plain `completed`) was chosen because the
gate requires either a real on-disk `--file-path` in the target repo or a
real, unmerged `--commit-sha`; there is no `claude-control` file artifact
here, and the audited commit is real and correctly unmerged -- this
accurately records "real AI-side work genuinely finished, nothing further
pending on the AI side; what remains open is the PR itself," matching this
status's own documented purpose (`UMR_STATUSES` comment, `superboss-register.py`).

## Remaining scope
None for this UMR. Redispatching a "fix + re-audit PR 305" task would
duplicate work that is honestly not yet ready to redo -- the extension-list
gap the FAIL verdict identified belongs to a future fix commit on PR 305 by
whoever owns that PR next, followed by a fresh independent audit at that new
head (the same "never trust a stale verdict" rule this task itself was
built to enforce). That is out of this RCA task's scope.

## Systemic note (not fixed here, same as fd89)
This is the **second** occurrence in the same governing chain
(UMR-20260813-200021-fd89 -> UMR-20260813-205208-feab) of
`resource_governor.py`'s terminal-classification sweep mis-reading a
cross-repo-only deliverable (commits or comments on an external repo, zero
`claude-control` diff) as "no real deliverable" and mechanically killing it.
A durable fix would teach that sweep to check the task's own recorded
`completed_steps`/`PROGRESS.md` for cross-repo evidence (PR comments, commit
SHAs in a non-`claude-control` repo) before concluding "orphaned, no
artifact" -- but implementing that generic detector is a separate, larger
piece of work than this RCA's scope; recorded here so it is discoverable the
next time this pattern recurs a third time.
