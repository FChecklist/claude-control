## Why the second invocation ended `blocked` instead of `completed`
The second invocation's own supervisor opened a PR
(`https://github.com/FChecklist/claude-control/pull/170`, still **OPEN**)
for the task's checkpoint branch in `claude-control` (the task's own repo,
per `task.yaml: repo: claude-control` -- a separate PR from the real
deliverable, which targets `FChecklist/veridian-scripts`). Automated
superboss review (`review.json`) correctly **rejected** it:

> "the actual diff does the opposite of [the stated task] and does not
> touch any decoy files at all: it adds a brand-new git submodule/gitlink
> entry (mode 160000) named 'veridian-scripts-clean' pointing at an
> external commit hash ... whose content is completely opaque to this
> review ... This is exactly the 'claim-registration commit' anti-pattern
> ... Introducing a git submodule is a supply-chain risk."

**Real root cause of the rejection:** the workspace's own checkpoint-commit
step ran a plain `git add`/`git commit` over the whole workspace, which
included the nested `veridian-scripts-clean/` clone (its own `.git/`
directory, no `.gitmodules` entry ever added). Git silently recorded that
nested repo as a nameless gitlink (mode `160000`) instead of either real
file content or a properly-registered submodule -- so the `claude-control`
tracking PR shows an opaque, content-free pointer even though the *real*
work (24 rewritten files, independently compile/syntax-verified) is
genuinely present, verifiable, and pushed on the `veridian-scripts` branch
noted above. This is a real, distinct defect in the generic
checkpoint-commit tooling (any task that clones a target repo into its own
workspace -- a standard, SPEC-encouraged pattern -- is exposed to the same
silent no-diff/gitlink trap), **not** evidence of fabricated work.
