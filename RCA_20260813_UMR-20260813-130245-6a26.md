## Why this is left as-is: not fixed, not redispatched, not marked terminal
Per this same repo's own already-established precedent for exactly this
situation (`RCA_20260813_stop_the_self_amplifying_rca_cascade.md`, section
D): a UMR representing real, actively in-flight worker execution is
deliberately **not** force-closed via `mark-umr-terminal` -- "forcibly
terminating a real, actively-running worker's row is a different, riskier
action... It was left to reach its own real terminal status through the
normal task lifecycle." The same reasoning applies here, with one added
wrinkle: this UMR's own `status` field already reads `killed` (not
`running`), because `scan_stuck_tasks()` writes that status directly at
kill time and nothing in `worker-exit-status-bridge.py`'s deliberately
conservative bridge (it only ever writes `status=failed`, and only for a
*self-reported* negative checkpoint status -- `in_progress` is not one)
reconciles it back once systemd auto-restarts the unit. That is a real,
known gap (the same "misleading status=killed" root cause already named,
but not fixed, in `RCA_20260813_UMR-20260813-104044-578b.md`), left
out-of-scope here for the same reason it was left out-of-scope there: this
task's real scope is RCA of one row's kill, not a platform-wide
UMR-status/restart reconciliation mechanism.

Given that:
- **Fix + redispatch is wrong**: there is nothing to fix in the killed
  attempt itself (it was not a bug, it was a fixed timeout hitting
  legitimately long real work), and redispatching now would start a
  *second* worker against the *same* branch/scope while the real,
  already-resumed worker (invocation 2/20) is actively mid-edit on that
  same branch -- a wasted, colliding duplicate dispatch, exactly the class
  of waste this repo's own target-identifier dedup guard
  (`veridian-scripts` PR #297) exists to prevent.
- **Marking a terminal outcome now is wrong**: no real deliverable exists
  yet to cite (`gh pr list` empty, workspace changes uncommitted) -- doing
  so would either fabricate a false `completed`/`completed_unmerged` or
  falsely record `failed` against work that is demonstrably still
  progressing. Both violate this task's own "do not fabricate completion"
  constraint.

**Action taken: none to the `umr_tasks` row.** The real remaining scope
(steps C-F of the original task) is already being executed by a live
worker right now; it will reach its own real terminal status (via
`mark-umr-terminal` once a real PR/commit exists, same as the 578b
precedent) through the normal task lifecycle, not through this RCA task
forcing a write.
